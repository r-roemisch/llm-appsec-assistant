# Milestone M6 report: feedback, evaluation, CI, documentation

Date: 2026-11-09. Scope per `docs/SPEC.md` section 17: `feedback` with Langfuse scores and the
admin dashboard, Evaluation Case conversion, `eval` with DeepEval, Guard metrics and the estimate,
GitHub Actions CI, README, guides, traceability with evidence links, critique log, recorded live
smoke run. Tests A18, A19, A22, A23. It also closes the last open item of the specification,
short-term memory summarisation (section 9), which earlier reports listed as not built.

## What was built

Backend (`src/rampart`):

- `feedback/`: thumbs up or down with an optional comment (secrets redacted) on a user's own
  finished answer, stored with the answer's trace id and the Tools it used, and sent to the trace
  as a `user_feedback` score whose id is the Feedback's id, so a changed thumb updates the score.
  The admin dashboard lists every rating with its question and answer; an admin turns an answer
  into an Evaluation Case (`qa` with a reference answer, or `tool` with the expected Tools),
  which keeps its own copy of the question. Feedback is deleted with its Conversation.
  `admin/digest.py` fingerprints the policy (Tool policies, settings, Slots, Models, Plugins)
  and the Guards' rules, so a test can show Feedback changes neither (A18).
- `eval/`: `rampart eval --suite qa|tool|guard|all [--limit N]` and the admin endpoints share
  one runner. `guard` replays the labelled inputs through the input Guard (precision, recall,
  F1, false-positive rate, recall by category, the held-out set separately). `tool` and `qa` run
  real Rampart turns as a throwaway user on a snapshot of the database and the vector store
  (SQLite's backup API), deleted afterwards, so evaluation never adds Conversations, usage or
  traces to the real data. `tool` scores DeepEval's tool correctness deterministically; `qa`
  scores faithfulness, answer relevancy, contextual precision and contextual recall with the
  judge Slot through Rampart's own Provider code, so each judge call records the cost OpenRouter
  reports. The retrieval context is the passages the answer was actually written from (the
  `graded` retrieval event now carries `context_ids`). Before a run the CLI and the admin page
  show an estimate at OpenRouter's listed prices and wait for a yes; the admin page refuses to
  start when the estimate changed since it was shown, allows one run at a time, and executes it
  in a separate process (DeepEval never loads in the web server). A run whose process
  disappeared is marked failed. Reports are Markdown and JSON in `docs/reports/eval/`; cases
  added from Feedback appear there by id only.
- `eval/` datasets: `qa_cases.jsonl` (30, written from the ingested Sources' passages),
  `tool_cases.jsonl` (20, five of them expecting no Tool), and the M3 Guard sets; `eval/README.md`
  is their dataset card.
- Short-term memory: a `memory` step at the start of each turn summarises older turns with the
  grader Slot once the model-facing history passes `RAMPART_HISTORY_SUMMARY_TOKENS` (6000
  estimated tokens), keeps the last `RAMPART_HISTORY_KEEP_TURNS` (3) user turns word for word,
  cuts only at a user message (a Tool call is never separated from its result), and presents
  the summary as a delimited note. The stored messages users see are untouched; a failed summary
  keeps the full history.
- Tracing: with Langfuse configured, every turn and score is also written to the JSONL log under
  the same trace id (A22: a trace survives a Langfuse outage); everything exported to Langfuse
  passes the SDK's mask hook with Rampart's secret redaction.
- CI (`.github/workflows/ci.yml`): actions pinned to release commits, a read-only token, the
  offline suite, and `rampart eval --suite guard` as a report step; frontend type check, lint,
  tests and build.

Frontend (`frontend/src`): thumbs up and down under each finished answer (not while it streams
or waits for an Approval), saved at once and rolled back if the server refuses; every rating opens
an optional comment form that says administrators see the rating with the question and the
answer, and that Feedback alone never changes how Rampart answers. An admin Feedback tab with
totals, filters, each rating with its question, the folded answer, Model, Tools, trace id and
where the score went, and the conversion dialog (`qa` with the expected answer prefilled from the
actual one and a warning to correct it, or `tool` with a checklist of the current Tools). An
Evaluation tab with dataset sizes, added cases, a new-run form that shows the per-suite estimate
(with a warning naming the judge and the money for `qa`) and a "Run for about $X" or "Run (free)"
confirmation, the runs list polling while a run is active, and a run dialog with metrics and the
rendered report. 39 new Vitest tests; `frontend/README.md` covers M6.

Documentation: README (scope and limits, feedback and evaluation, commands), user guide
(Feedback, memory), admin guide (Feedback and Evaluation Cases, evaluation, memory, tracing,
shared-host advice), `docs/API.md` (M6), `docs/SPEC.md` section 20, `docs/traceability.md`,
`docs/critique_prompt.md`, `docs/critique_log.md`, `eval/README.md`; `docs/DESIGN.md` marked as
the historical record it is.

## Decisions made during the build

- **DeepEval through its metrics, not through pytest.** The spec says `rampart eval` runs DeepEval
  "through pytest". Its metrics are called directly instead (`a_measure`), so the CLI and the
  admin page share one runner and every score, reason and cost lands in one JSON report. Rampart's
  own test suite disables DeepEval's pytest plugin, which otherwise loads into every pytest
  session and opens a telemetry run.
- **DeepEval kept on a short leash.** Before it is imported: telemetry off, no reading of `.env`
  files (it otherwise copies them into the process environment), its cache folder inside the run
  folder, no Confident AI upload. It never loads in the web server; a test checks that.
- **The judge moved to `openai/gpt-6.1-sol`.** The first real QA run showed this OpenRouter
  workspace blocks `anthropic/claude-opus-5.5` (HTTP 404, guardrail and data policy), the same
  guardrail that ruled out other Models in M1. `gpt-6.1-sol` is the catalog's other powerful-tier
  Model. Chat and judge are now both OpenAI Models; same-vendor judging can favour that vendor's
  style, which the admin guide says. A preflight now checks the judge with one tiny request before
  any turn is paid for.
- **Snapshots, not a test user in the real database.** Evaluation turns would otherwise add
  Conversations, usage and traces to the data admins look at.
- **Feedback cases by id in reports.** Their questions come from users' Conversations, and
  reports land in a folder that is likely to be committed.
- **The grader is built whenever its Slot is available** (not only when retrieval needs it), so
  the memory step can summarise with the cheap Model. It makes no call unless needed.

## Found and fixed during the build

- **A22 had gaps.** Langfuse was used instead of JSONL, not as well, so a configured but
  unreachable Langfuse lost traces: now JSONL is always written. An Ollama outage read
  "ConnectError: All connection attempts failed": now it names the model and the Ollama address
  and says how to start it. The retries (two, with the OpenAI client's backoff, 120 s timeout)
  were configured but untested: now pinned by a test.
- **The critique found three data-protection gaps** (`docs/critique_log.md`, point 5): uploaded
  documents and the Project Profile were not secret-redacted before reaching prompts and
  embedding calls, and Langfuse received raw model output from the LangChain callback. All three
  are fixed with canary tests. It also led to: a Target URL may carry nothing but a port (a
  `user@host@127.0.0.1` URL used to be accepted), the harness ignores proxy variables and never
  follows redirects, a test that an Approval does not survive a policy change, and one
  cross-user test over 14 routes.
- **A weak test found by mutation.** The memory test still passed when the summary dropped every
  turn but the current question, because by the fourth turn the history happened to match again.
  It now checks what the model received on every turn.
- **Langfuse Cloud retired `GET /api/public/scores`** (HTTP 410) for `/api/public/v3/scores`;
  found while reading the A18 score back.

## Not done or not verified

- The full 30-case QA evaluation (about $2 at list prices) has not been run; only the first
  three cases. The judge has not been calibrated against human ratings.
- Datasets are small and written by one author (`eval/README.md`).
- From the critique, deliberately left: an ownership challenge for Targets, an OS sandbox for
  Plugins, a committed browser test suite, a written data-flow inventory and a trace retention
  policy (`docs/critique_log.md`).
- "Agent learns from feedback" is met only as a human-in-the-loop cycle (Feedback, Evaluation
  Case, next run, a maintainer's change), as the specification intends; nothing adapts
  automatically.
- Nothing is committed.
