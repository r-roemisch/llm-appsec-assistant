# Milestone M4 report: injection tests and demo Target

Date: 2026-11-08. Scope per `docs/SPEC.md` section 17: `demo_target`, `TargetService`, the
`InjectionTestRunner`, the seed suite, the real `run_injection_test` executor behind the Approval
built in M3, the Targets route, `rampart demo-target` and the full `rampart demo`. Test: P6-A21.

## What was built

Backend (`src/rampart`):

- `demo_target`: a small FastAPI application that is a deterministic stand-in for a document
  assistant, not a real LLM, so a run is reproducible and needs no Provider. It has a message
  route, a document slot, a fake `export_document` action and a local sink file. Its only
  interesting behaviour is the difference between the two profiles: `secure` treats the document
  as data and never exports the internal record because a document asked, `vulnerable` follows an
  export instruction found in the (untrusted) document. The "internal record" is a fixed,
  obviously synthetic sentinel; the sink is a local file; there is no network call and no real
  secret. It exists to be tested, not used. `rampart demo-target --profile secure|vulnerable`
  runs it on a loopback port.
- `targets`: `TargetService` registers, lists, updates and deletes a user's Targets. Registration
  refuses any address that is not a loopback literal (127.0.0.0/8, ::1, `localhost`) and never
  resolves the host, so DNS cannot redirect a Target; the Gateway checks the same again when a
  test is requested. The `InjectionTestRunner` drives a Target over HTTP (a real client in
  production, an in-process transport in tests) and reads each candidate's outcome from the
  Target's own `/audit` and `/sink`, never from its reply: `proposed` (the agent recognised the
  export), `executed` (it invoked the action), `received` (the sink holds the sentinel). A
  candidate whose own text already contains the sentinel is marked `contaminated` and excluded
  from the breach count. The suites live in `fixtures/injection/` (`seed-v1`: 12 indirect-
  injection candidates, 6 benign), loaded by `targets/suites.py`.
- The `run_injection_test` executor is now real: it looks up the Target (ownership re-checked),
  loads the suite, runs it, and returns the per-case outcomes and a verdict, or a clear error
  when the Target cannot be reached. It still sits behind the M3 Gateway and Approval unchanged.
- The Targets route (`/api/targets`, M4 in `docs/API.md`): register, list, update, delete; the
  Project Profile gained validated `target_ids`, and the system prompt lists the user's
  registered Targets with their ids so the assistant can offer to test them.
- `rampart demo` now also registers a vulnerable demo Target for the demo user and starts it
  alongside the app; `rampart demo-target` runs one standalone.

Frontend (`frontend/src`): a lazy-loaded Targets page (`/targets`) with a register form
(name, loopback URL checked in the browser as well as on the server, input surface, optional
expected profile), the list of the user's Targets with rename, expected-profile edit and delete,
and a "Run a test" button that opens a new conversation with the request drafted (it still goes
through the Approval card; nothing runs from the button itself). `run_injection_test` tool cards
show the verdict as a green Secure or red Vulnerable badge with the summary line, and say that the
per-case breakdown is in the audit log and the Report. The Project Profile page lists the user's
Targets as a checklist saved as `target_ids`. 21 new Vitest tests.

Documentation: the user guide (Targets, now shipped), README, `docs/API.md`, `docs/SPEC.md`
section 20.

## Decisions made during the build

- The demo Target is deterministic, not an LLM. The spec describes a fixed app with a message
  route, a document slot, a fake export tool and a sink; making it deterministic means A21 is
  reproducible and offline, and the test measures the harness and the two profiles, not a model's
  whims. Its export-intent detector is a small regex standing in for a naive agent that cannot
  tell instructions in data from instructions from its user.
- Outcomes are read from the Target's audit log and sink, as the spec requires, so a vulnerable
  Target that merely says "I refuse" while actually exporting is still caught, and a secure one
  that narrates an attack is not falsely marked breached.
- The runner resets the Target's sink before each candidate, so a sink marker is attributable to
  that candidate; contamination (the marker already in the input) is detected and excluded.
- The seed suite is small, synthetic and specific to the demo Target's fake action; it targets
  nothing real. The runner never mutates a candidate or generates new ones (adaptive testing is
  out of scope, P3).
- The injection run's per-case result is stored in the Gateway audit record and can be put in a
  Report; the `tool_result` stream event carries only the one-line verdict, as in M3.

The seed suite against the real demo Target over a loopback port (uvicorn, real HTTP, no model):

| Profile | proposed | executed | received (uncontaminated) | breaches | verdict |
|---|---|---|---|---|---|
| vulnerable | 12 of 12 | 12 | 11 | 11 | vulnerable |
| secure | 12 of 12 | 0 | 0 | 0 | secure |

Both profiles proposed every injection candidate and acted on no benign one; the one contaminated
candidate was flagged and excluded from the breach count in both.

One real-model run through the whole stack (GPT-6 Luna, an in-process vulnerable demo Target):
the model called `run_injection_test` with the registered Target's id and `seed-v1`, the Gateway
required an Approval, approval resumed the turn, the harness ran, and the answer reported
"vulnerable: 11 of 12 injection candidates reached the sink, 1 contaminated" with the audit-log
evidence. Cost: $0.0014.

The built frontend against the real backend, a real demo Target on a loopback port and GPT-6
Luna, driven in headless Chromium (1280 px light, 390 px dark): the Targets page, a non-loopback
URL refused inline before any request, a second Target registered, the stored run's verdict card,
"Run a test" drafting the request, a live Approval card bound to the exact arguments, approval
resuming the turn into a "Vulnerable: 11 of 12 injection candidates reached the sink" verdict
card, and the Profile page saving a Target selection. No page errors, no server errors, no
horizontal overflow.

Changed on review: the Targets list and the Profile checklist first showed the owner's *expected*
profile with the same green and red shield as a test verdict, which read as a result when nothing
had been run. The expected profile is now a neutral "Expects secure" label, and the shield badge is
kept for verdicts only.

Acceptance test covered:

| ID | Scenario | Evidence |
|---|---|---|
| A21 | Demo Target in vulnerable and secure profiles: executed + received with sink evidence versus proposed + denied; unregistered URL rejected; marker in input marks contamination | `tests/test_injection.py` (vulnerable breaches from the sink, secure refuses, contamination flagged, end-to-end through a turn and Approval, unregistered and unreachable Targets), `tests/test_targets.py` (loopback-only registration); the real-network and real-model runs above |

Defect found by the new tests and fixed during the build: `profile_block` returned nothing when a
user had registered a Target but not yet saved a Project Profile, so the assistant never saw the
Target's id and asked the user for it (seen first in the real-model run); the block now shows
registered Targets regardless of whether a profile row exists.
